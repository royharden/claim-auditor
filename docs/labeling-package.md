## Operator procedure after activation

The six original DEV families are described in [corpus-dev.md](corpus-dev.md). Use only a family's `source/` as audit input; keep provenance/review prompts and later judgments out of inference. Start with original README bytes and account for every assertion, including any extractor omission; an extracted inventory alone cannot establish complete annotation coverage.

The source API below is intended for a later authorized local operator session. These are proposed calls, not commands run or evidence of a completed review. CLI wiring is owned by the shared CLI maintainer and must follow the published signatures.

1. Produce a complete local audit under the normal activation rules, then call `prepare_annotation_package(run_root, fresh_out, family_id="dev-...")`. The parent of `fresh_out` must already be an ordinary directory. The function invokes the existing `verify_report` resolver, rechecks the report-byte identity, copies frozen included source, and writes per-claim source/evidence files. It writes `PACKAGE.json` last and returns its exact-byte SHA256. A partial directory with no completion file is not a ready package. No package has been generated by running this function during Dirty Mode.
2. Deliver the local package privately to the actual reviewer. It contains the original source tree, snapshot and inventory, exact Claim objects, per-subject evidence/coverage bundles and digest bindings. It contains no prefilled verdicts, human identity, action receipt or human sign-off. Code evidence may influence review, so this is transparent annotation, not a blinded model comparison. Inspect omission/unsupported blocks as well as listed subjects. Add an omitted atom only with validated original-byte coordinates, complete qualifiers and its own reviewed evidence bundle; never invent coordinates.
3. A reviewer supplies a judgment using the existing `GoldAtom` fields: stable subject/family identity, exact Claim, expected verdict and relation, answerability, full supported/unresolved/accused predicate accounting, annotator type/ID, rationale, actual date and preserved disagreements. Agent preliminary judgments remain `agent`. The service never turns these into human rows automatically.
4. Build `make_ruling(atom, source_manifest_digest=..., evidence_digest=..., recorded_at=..., supersedes_ruling_id=..., human_action_id=...)`, using digests from reopened package bytes. `claim_digest` is the SHA256 of canonical Claim JSON without a trailing newline; package evidence digests include the exact trailing newline in each evidence file. A real human review needs an actual operator action identity and adjudication date; only then may the operator explicitly confirm the append/import. Store the ledger outside inference inputs and tracked source fixtures.
5. Use `append_ruling(ledger, ruling, human_confirmation=False)` for agent judgments; real human writes require explicit `human_confirmation=True`. `import_rulings(ledger, incoming_history, human_confirmation=...)` validates the complete incoming history and appends new rows. `export_rulings(ledger, fresh_out)` writes the full validated history to a new file and returns its SHA256; it never replaces an existing output. No human confirmation option should default to true.
6. Call `current_rulings` only with independently reopened current source/claim/evidence digests. It returns latest judgments per annotator. Preserve their differences for actual independent adjudication; do not feed all annotators' competing judgments as if they were distinct gold claims. No automatic scorer gold export is provided. The final curator still owns rights, family grouping, complete source coverage, actual human review and release admission.

`load_rulings` verifies complete history and revision chains, including content-addressed IDs. Changed underlying bytes require a new ledger and fresh review. Ledgers are limited to one source manifest; separate families/snapshots generally use separate ledgers. Operator directories require normal local ownership/access controls. The exclusive sidecar lock coordinates cooperating writers; a stale lock or failed write requires a visible recovery decision, never automatic history deletion.

Future validation must exercise source/evidence tamper, changed-claim conflicts, stale supersession, conflicting annotators, preserved disagreement history, idempotent import, fresh export refusal, human confirmation/date requirements, partial-tail refusal, busy writer and crash behavior. No such runtime validation, human adjudication, heldout custody or comparative score has occurred here. Preparing this DEV package does not authorize private source transfer, external accounts, publication, provider use or spending.
